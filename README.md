# Lampa: Аниме онлайн + Кино онлайн (HDrezka прямым потоком)

Три части в одном репозитории:

- **anime_online.js** (v1.23.0) — кнопка «Аниме онлайн» на карточке (AniLibria, YummyAnime, YummyAnime.TV). У YummyAnime и YummyAnime.TV озвучка и серия выбираются в Lampa, а видео играет её собственный плеер: сервис на VPS отдаёт прямые HLS-ссылки плеера Kodik.
- **kino_online.js** (v2.2.2) — кнопка «Кино онлайн»: фильмы и сериалы **HDrezka прямым HLS-потоком**; если сервер недоступен — запасной источник Kinokrad (плеер окном).
- **kino_extractor.py** (v1.10.1) + **worker.js** — серверная часть: экстрактор HDrezka, разбор Kodik и видео-прокси (HLS) на VPS, CORS-прокси и мост на Cloudflare.
- **cub_vps.js** (v1.0.0) — запросы CUB идут через наш VPS: без этого карточка фильма виснет, потому что `cub.*` из РФ недоступен.
- **slow_check.js** (v2.0.0) — диагностика: журнал сетевых запросов (Настройки → «Журнал запросов»).

## Как работает «Кино онлайн» 2.0.0

1. Кнопка **«Кино онлайн»** на карточке фильма.
2. Поиск по названию на HDrezka через свой экстрактор (см. ниже).
3. Выбор фильма или сериала (в подписи год и тип).
4. Выбор озвучки (у фильмов до 10 вариантов, у сериалов до 20).
5. Для сериалов — выбор сезона и серии.
6. Воспроизведение в **штатном плеере Lampa** (hls.js): без iframe, без рекламы чужих сайтов, переключение качества прямо в плеере.
7. Если экстрактор недоступен — плагин уходит на запасной источник **Kinokrad** (плеер открывается окном, как в версии 1.x).

## Серверный экстрактор: зачем он нужен

HDrezka закрыта тремя защитами, которые браузер телевизора обойти не может:

| Защита | Что происходит | Как обходим |
| --- | --- | --- |
| Антибот **Anubis** (proof-of-work) | Запрос без пройденного челленджа получает страницу-заглушку | Экстрактор решает `sha256(randomData + nonce)` с нужным числом ведущих нулей и получает cookie `techaro.lol-anubis-auth` |
| Гео-замок по `CF-Connecting-IP` | Не-РФ/СНГ адрес получает `success: true`, но `url: false` — потока нет | Экстрактор подставляет в этот заголовок **IP клиента** (адрес, с которого пришёл запрос плагина) |
| Привязка ссылки к IP клиента | CDN `stream.voidboost.one` отвечает 404, если манифест запрашивает «не тот» адрес | Видео качает **сам телевизор**: ссылка минтится под его адрес, и CDN видит тот же адрес |

Отсюда главное ограничение: **поток нельзя проксировать** через сервер — сервер только выдаёт ссылку.

### Ручки экстрактора

Все запросы идут через `/kino/<token>/`:

| Ручка | Параметры | Ответ |
| --- | --- | --- |
| `/health` | — | состояние, версия, IP заказчика |
| `/search` | `q`, `limit` | список фильмов и сериалов |
| `/info` | `url` | id, озвучки, сезоны, признак сериала |
| `/episodes` | `url`, `translator`, `season` | список серий выбранного сезона |
| `/stream` | `url`, `translator`, `season`, `episode` | ссылки на HLS по качествам и субтитры |

Пример:

```bash
curl "https://<адрес>/kino/<token>/search?q=Интерстеллар&limit=3"
```

### Развёртывание на своём сервере

```bash
# 1. сервис
install -m 755 kino_extractor.py /opt/kino-extractor/kino_extractor.py
echo '{"token": "СВОЙ_ТОКЕН", "port": 8791}' > /etc/kino-extractor.json
chmod 600 /etc/kino-extractor.json

# 2. systemd
cat > /etc/systemd/system/kino-extractor.service <<'UNIT'
[Unit]
Description=kino-extractor (HDrezka для Lampa)
After=network-online.target

[Service]
ExecStart=/usr/bin/python3 /opt/kino-extractor/kino_extractor.py --config /etc/kino-extractor.json
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
UNIT
systemctl enable --now kino-extractor

# 3. nginx: http на 80 и https на 8443
#    сертификат Let's Encrypt на имя вида 94.156.237.213.nip.io (webroot + certbot)
```

Адрес экстрактора задан в `kino_online.js` в массиве `EXTRACTORS`: первый — свой адрес
с точным IP клиента, второй — мост через Cloudflare Worker (`/kino/*` в `worker.js`,
он передаёт адрес клиента в заголовке `X-Kino-Client-IP`).

Cloudflare Worker **не может** обращаться по голому IP (ошибка 1003), поэтому в `worker.js`
сервис указан именем (`http://94.156.237.213.nip.io`), а не `http://94.156.237.213`.

### Вход в аккаунт HDrezka (качества выше 480p)

Гостю сайт отдаёт только 360p и 480p — это его тарифная сетка, а не ограничение плагина. С аккаунтом
качества выше, премиум даёт максимум. Вход делает сам сервис: логин и пароль лежат в конфиге, сессия
живёт в памяти службы и переиспользуется вместе с cookies Anubis.

```bash
# 1. дописать в конфиг (файл доступен только root)
python3 - <<'EOF'
import json
path = "/etc/kino-extractor.json"
data = json.load(open(path))
data["rezka_login"] = "ваш_логин"
data["rezka_password"] = "ваш_пароль"
json.dump(data, open(path, "w"), ensure_ascii=False, indent=2)
EOF

# 2. перезапустить и проверить
systemctl restart kino-extractor
curl -s "https://<адрес>/kino/<token>/health"   # ждём "rezka_user": true
journalctl -u kino-extractor | grep "вход в HDrezka"
```

Проще всего — **с телевизора**: Настройки → Кино онлайн → «Логин HDrezka» / «Пароль HDrezka». Плагин
отправит их на сервис, сервис залогинится и сохранит вход в конфиг. Пароль при этом остаётся в настройках
Lampa открытым текстом — это плата за удобство; если это важно, вписывайте вход прямо в конфиг (ниже).

`/stream` отдаёт ровно те качества, что вернул сайт, поэтому после входа в плеере появятся новые пункты. Если вход не удался, в журнале будет причина от сайта («Введен неверный
email или пароль» и подобное), а сервис продолжит работать как гость.

Два ограничения, о которых стоит знать: сессия живёт на сервере (Франкфурт), и если сайт привяжет её
к адресу, вход придётся повторять; а аккаунт, который логинится с адреса датацентра, теоретически
может попасть под проверку сайта.

## Второй источник кино: Aprel Kino (720p)

Rezka без аккаунта отдаёт только 360p/480p, поэтому добавлен второй источник —
`aprelteam.gokino.by` («Aprel Kino», DLE-сайт). Гостям страницы фильмов там закрыты, поэтому
сервис логинится сам, забирает страницу фильма и достаёт прямой `master.m3u8` из плеера
`api.variyt.ws/embed/kp/<id>`.

- Качество: обычно **720p + 360p** (у части старых фильмов 540p/270p).
- Ссылка **не привязана к IP** — видео качает сам телевизор, сервер только добывает адрес.
- Вход: поля «Логин Aprel Kino» и «Пароль Aprel Kino» в настройках плагина — пароль хранится
  только в настройках Lampa, сервис держит его в памяти и на диск не пишет (в журналах его нет).
  При желании можно прописать `aprel_login`/`aprel_password` в `/etc/kino-extractor.json` вручную.
- Меню источников появляется само, если сервер авторизован: плагин спрашивает `/health`
  и смотрит поле `aprel_user`. Вводить пароль на телевизоре не обязательно.
- Проверено: поиск «Железный человек» → 15 карточек, поток 720p/360p, плейлист открывается
  с другого IP (не привязан), вход под ником работает (под email сайт не пускает).

## Аниме онлайн (anime_online.js)

| Источник | Токен | Как воспроизводится |
| --- | --- | --- |
| AniLibria | не нужен | прямые HLS 480p/720p/1080p в плеере Lampa, плейлист серий |
| YummyAnime.TV | не нужен | Kodik прямым HLS в плеере Lampa: озвучка и серия выбираются в Lampa |
| YummyAnime | не нужен | Kodik прямым HLS в плеере Lampa, остальные плееры (Alloha, CVH, Sibnet) — окном |

Прямой XHR к `kodikplayer.com` из Lampa браузер режет (нет CORS-заголовков), поэтому ссылки
минтит сервис на VPS: плагин отдаёт ему ссылку плеера, сервис отвечает готовыми HLS-ссылками
(360p/480p/720p), а видео играет штатный плеер Lampa — работает пульт, нет чужой рекламы.
Ссылки Kodik не привязаны к IP и не требуют Referer, так что телевизор качает поток сам.

Ссылки плеера Kodik приходят в двух видах: `/serial/<id>/<hash>` (страница релиза) и
`/season/<id>/<hash>` (такой отдаёт YummyAnime — это озвучка + сезон); сервис разбирает оба.

## Прокси Cloudflare

`worker.js` умеет два маршрута: `/proxy?url=` — CORS-прокси для плагинов (только домены
из белого списка: `api.yani.tv`, `yummyanime.tv`, `kinokrad.cc`, `kinogo.*`, домены Kodik)
и `/kino/*` — мост к экстрактору на VPS для случаев, когда телевизор не может достучаться
до сервера напрямую.

## CUB через VPS (cub_vps.js)

Lampa на карточке фильма запрашивает у CUB блок «Реакции» (`/api/reactions/get/...`) и, если
ответа нет, карточка виснет (issue yumata/lampa#256). Из РФ домены CUB (`cub.best`, `cub.red`,
`cub.black`, `durex.monster`) не открываются, поэтому запросы уходят в никуда.

`cub_vps.js` подменяет адрес таких запросов на наш сервер, а сервер уже сам спрашивает CUB:

| Запрос Lampa | Куда идёт с плагином |
| --- | --- |
| `https://cub.best/api/...` | `https://94.156.237.213.nip.io:8443/cub/api/...` |
| `https://tmdb.cub.best/3/...` | `https://94.156.237.213.nip.io:8443/cubtmdb/3/...` |
| `https://cub.black/plugin/...` | `https://94.156.237.213.nip.io:8443/cub/plugin/...` |

Остальные запросы (TMDB, картинки, наши плагины) не трогаются. Реализовано перехватом
`XMLHttpRequest.open`, `fetch`, `setAttribute('src')` и сеттера `src` у скриптов, картинок и iframe.

На стороне сервера это два `location` в `/etc/nginx/conf.d/kino-https.conf`: `/cub/` →
`https://cub.best/` и `/cubtmdb/` → `https://tmdb.cub.best/` с подменой `Host`/SNI, CORS
(эхо `Origin`, `Allow-Credentials`, предварительный `OPTIONS` → 204) и поддержкой WebSocket.

Проверено с домашнего IP через прокси: реакции `movie_157336` — 200 и те же 539 байт, что и
напрямую с `cub.best`; TMDB-прокси `3/configuration` — 200; POST и скрипты плагинов CUB
(208 КБ JS) отдаются. Тест подмены адресов: 13 случаев (зеркала, `tmdb.*`, чужие домены вида
`cub.best.evil.com`, повторный проход) — 0 ошибок.

## Видео через наш сервер (anime 1.16.0 + сервис 1.4.1)

Провайдер закрывает CDN Кодика (`solodcdn.com`): телевизор получает от сервиса ссылку на поток, плеер открывается — и закрывается, потому что сам поток скачать не может. На компьютере тот же адрес открывается только через AntiZapret, у телевизора его нет. Поэтому видео Кодика по умолчанию идёт через наш сервер:

- `playlist.m3u8?url=<плейлист>&base=<наш адрес>` — сервис скачивает плейлист с CDN и переписывает все ссылки на нас; отдаёт с типом `application/vnd.apple.mpegurl` (иначе AVPlayer на Apple TV считает ответ текстом и не играет).
- `segment.ts?url=<кусок>` — сервис отдаёт сегмент как `video/mp2t`. Прежние имена `/hls` и `/segment` работают как синонимы.
- В плагине переключатель `VIDEO_VIA_SERVER` (в начале блока плеера): по умолчанию `true` — видео всегда через наш сервер; `false` — играть напрямую, если у зрителя CDN открыт (тогда плагин ещё и проверяет доступность сам, `fetch` в режиме `no-cors`).
- При первом включении видео в сессии показывается уведомление «Видео идёт через наш сервер».

Проверка сервиса: плейлист через `/playlist.m3u8` — 200, `application/vnd.apple.mpegurl`, 85 348 байт, 237 сегментов, ссылки ведут на наш `/segment.ts`; сегмент через `/segment.ts` — 200, `video/mp2t`, 2 605 304 байта, первый байт `0x47` (MPEG-TS).

## Журнал с телевизора (anime 1.17.0 + сервис 1.5.0)

Плагин сам сообщает на наш сервер, что происходит на телевизоре — фотографировать экран не нужно:

- Сервис: ручка `/log?kind=<вид>&msg=<текст>` дописывает строку в `/var/log/kino-plugin.log` (файл растёт до 2 МБ, потом уезжает в `.1`).
- Плагин аниме пишет: `load` (версия плагина и User-Agent телевизора), `play` (серия, качества, адрес потока), `video` (состояние видеоэлемента через 4, 12 и 25 с: `readyState`, `networkState`, код ошибки, время, размер кадра), `js-error` (ошибки в плеере), `fail` (Kodik не отдал поток, ушли окном).
- Плагин-проверка `anime_check` пишет `check` — все строки своего отчёта одной строкой.
- Читать: `grep -h "kino-plugin" /var/log/*` не нужен — `tail -30 /var/log/kino-plugin.log`.

## Почему не открывался плеер: цикл в записи (anime 1.19.0)

Симптом: серия «начинает загружаться» и выбрасывает назад, видео нет никогда.

Причина нашлась по журналу с телевизора — плагин 1.17.0 прислал строку:

```
js-error | Lampa.Player.play упал: JSON.stringify cannot serialize cyclic structures.
```

Плеер Lampa сохраняет своё состояние через `JSON.stringify`, а в запись потока попадали ссылки на себя:

- `card: movie` — объект фильма Lampa ссылается сам на себя (`movie.card` → `movie`);
- `entry.playlist = [entry]` — запись ссылалась на саму себя.

Оба варианта роняли `Lampa.Player.play`, поэтому плеер не открывался вообще.

Как сделано теперь: карточка собирается «плоской» (`plainCard` — только простые поля: id, source, title, постер и т.п.), `timeline` прогоняется через JSON-копию, плейлист — отдельные записи без ссылок на себя, а перед запуском запись проверяется на сериализуемость (`safeEntry`: если не сериализуется — убираются `card` и `timeline`). Та же чистка добавлена в кино-плагин (2.0.1) и в проверку (1.0.3).

## Бесконечная загрузка плеера: мост в видео и медленная отдача сегментов

После починки цикла плеер Lampa стал открываться, но застревал на загрузке. Что показал журнал:

- `play-step | плеер открылся` / `плейлист отдан` — плеер открывается, запись принимается;
- `video | +1…+25с: видео-элемента нет` — сам видеоэлемент в этот момент не найден;
- в логах nginx: плейлист и сегменты запрашивались **через Cloudflare-мост** (`104.23.x`), потом загрузка обрывалась.

Вывод: мост — плохой транспорт для кусков по 2–3 МБ. Поэтому видео теперь всегда идёт по **прямому** адресу VPS (`streamBase()` больше не смотрит на выбранный адрес API), а отчёты — по прямому адресу с запасным маяком `Image`.

Заодно сервис (1.5.1) отдаёт сегменты **по мере скачивания** (чанки по 64 КБ), а не после полной загрузки: первый байт приходит примерно за 0,3 с, весь сегмент 2,6 МБ — за 2,2 с. Проверка сервиса: ссылки на поток 0,39 с, плейлист 0,39 с / 85 348 байт / 237 сегментов, сегменты 1–3 — MPEG-TS (`0x47`).

Проверка плейлиста, который получает плеер: `#EXTM3U`, `#EXT-X-VERSION:3`, `#EXT-X-PLAYLIST-TYPE:VOD`, `#EXT-X-ENDLIST`, 237 сегментов, шифрования нет, BOM нет, тип `application/vnd.apple.mpegurl`.

## Подгрузки при просмотре: кэш сегментов и выбор качества (аниме 1.21.0 + сервис 1.6.2)

Видео идёт двумя плечами: сервер тянет кусок с CDN, потом отдаёт телевизору. Если CDN отвечает неровно, второе плечо простаивает — отсюда подгрузки. Что сделано:

- сервис держит **кэш сегментов в памяти** (до 96 МБ) и **заранее скачивает следующие 2–3 куска** (`remember_order` запоминает порядок из плейлиста, `prefetch_after` греет кэш, `seg-N` разбирается и без плейлиста). Плееру кусок приходит из памяти, а не после похода к CDN;
- ответы помечаются `X-Cache: hit/miss` — видно, попал ли кусок в кэш;
- в настройках плагина появился пункт **«Качество потока»** (`anime_quality`): авто (до 720p), 720p, 480p, 360p. 480p и 360p в 2–3 раза легче — это главный рычаг, если канал до сервера узкий.

Проверено: после открытия серии служба подготовила 16 сегментов вперёд (примерно по 600 КБ), а плеер забирал следующие куски из кэша; подряд идущие сегменты отдаются за 0,36–0,67 с (первый, холодный — 2,23 с).

## Где выбирается качество (аниме 1.22.0)

Само качество не переключается: адаптации под скорость канала нет, поток выбирается один раз при запуске серии. Мест выбора три:

1. **Настройки → Аниме онлайн → «Качество потока»** (`anime_quality`) — с каким качеством запускать серию.
2. **Настройки Lampa → «Качество видео по умолчанию»** (`video_quality_default`, значения 480p/720p/1080p/2160p, по умолчанию 1080p). Плеер Lampa внутри `Player.play` вызывает `getUrlQuality(data.quality, false)` и **подменяет ссылку** на совпадающее качество — то есть при совпадении ключей эта настройка перебивает выбор плагина.
3. **В самом плеере** — кнопка «Качество» (список берётся из переданных качеств), переключение на ходу.

Чтобы выбор из плагина был главным, `qualityWithin()` при фиксированном качестве (480p/360p/720p) отдаёт плееру только качества **не выше выбранного**: подменить будет нечем (в Lampa по умолчанию 1080p, такого ключа в списке нет), а переключатель в плеере остаётся в этих пределах.

## Безопасность сервиса (экстрактор 1.7.0 + лимиты nginx)

Токен в плагине **не является секретом**: плагин раздаётся с GitHub Pages, адрес сервиса видит любой, кто его откроет. Поэтому защита строится не на секретности адреса, а на том, сколько запросов и с какой скоростью сервис согласен обслуживать.

Что закрыто:

1. **Видео-прокси больше не открытый фетчер.** `/hls?url=` и `/segment.ts?url=` тянут только те хосты, которые сервис сам выдал зрителю (`/kodik_url`, `/stream`, `/kodik`) или которые встретились в уже полученном плейлисте. Плюс базовый список CDN (`solodcdn.com`, `voidboost.one`, …) — он нужен, если телевизор дёрнет старый плейлист сразу после перезапуска службы. Всё остальное — 403. Это же закрывает SSRF: адреса в localhost, приватные сети и метаданные хостера отклоняются. Список расширяется без правки кода — ключ `proxy_hosts` в `/etc/kino-extractor.json`.
2. **Лимиты на nginx.** По IP: 8 запросов/с на JSON-ручки (всплеск 25), 25 запросов/с на видео (всплеск 60), 12 запросов/с на CUB, не больше 16 соединений; сверх — 429. Сегменты отдаются не быстрее 8 МБ/с на соединение (первые 6 МБ — без ограничения), чтобы один зритель не выжимал канал.
3. **Методы и мелочи.** На `/kino/` только GET/HEAD/POST/OPTIONS, на видео — только GET/HEAD; тело запроса ≤128 КБ; версия nginx не отдаётся; точечные файлы (`/.env` и подобное) — 404. IP из заголовков (`X-Kino-Client-IP` и т.п.) принимается, только если это действительно IP: иначе подставным заголовком можно было испортить журнал и попросить ссылку под чужой адрес.

Что осознанно **не** закрыто:

- Токен остаётся в коде плагина — убрать его нельзя, не сломав установку одной ссылкой. Он даёт доступ к JSON-ручкам, но не к произвольным адресам (п. 1) и не бесплатно (п. 2).
- Запросы через мост Cloudflare приходят с адресов Cloudflare: лимит по IP для них общий, а в журнале виден адрес моста, а не зрителя. Видео через мост больше не идёт — только JSON.

Журналы отдельные, чтобы не тонуть в сканерах с порта 80:

```bash
tail -20 /var/log/nginx/kino-access.log        # кто ходил и с каким кодом
grep "limiting requests" /var/log/nginx/kino-error.log   # кого притормозили лимиты
journalctl -u kino-extractor | grep отказал    # что не пустил видео-прокси
```

Трафик по адресам:

```bash
awk '{print $1}' /var/log/nginx/kino-access.log | sort | uniq -c | sort -rn | head
```

**Пароли в репозиторий не попадают.** Репозиторий публичный, поэтому логины и пароли живут только
в `/etc/kino-extractor.json` на сервере и в настройках Lampa. В коде допустимы лишь заглушки
(`test`, `demo`, `example`, `placeholder`). Перед коммитом стоит включить проверку:

```bash
git config core.hooksPath .githooks
```

Хук `.githooks/pre-commit` не даст закоммитить присвоение пароля в кавычках (ложное срабатывание обходится `--no-verify`).

Конфиг nginx лежит в репозитории: `nginx/kino-https.conf` и `nginx/kino-proxy.conf` (копировать в `/etc/nginx/conf.d/` и `/etc/nginx/snippets/`).
